## 一、项目是什么

`juju114514/qq-bridge` —— 一个把 QQ 接到 DeepSeek Harness（DSH）的桥接，**个人 fork**，
上游是 `Derpyu520/qq-bridge`。

它现在有三条入口：

| 入口 | 状态 |
| --- | --- |
| 个人号 QQ（SnowLuma / OneBot） | 稳定，日常在用 |
| QQ 官方机器人（Bot API v2） | 代码已实现，**仓库上锁**（缺真机 e2e） |
| DSH 插件模式（在 DSH 进程里跑） | 可用，安全边界三层 |

## 三、已知问题（按严重度，都有证据）

### P0-1 分叉漂移：401 vs 92

- 上游 2026-10-30 合了 PR #131（34 提交，安全批次 #78–#88 + 人格卡 + DSH 端口自愈），**我们没有它**
- 我们靠**自研**覆盖了其中 9/10 项（净化/令牌片段/不可信外壳/发送链/幂等/owner 门/黑话隔离/人格卡/端口自愈）
- **真缺口只有 1 条**：媒体抓取端口白名单（0.4.33 已补）
- 但结构性风险还在：**两条线越走越远**，上游的安全修复我们不会自动收到；我们的修复上游也拿不到

### P0-2 `bridge.js` 8,743 行

一个文件里同时装着：消息接入、会话状态、prompt 拼装、工具实现、HTTP 路由、官方通道编排、插件 sidecar。
今天修的问题里，**至少 3 个**是"改 A 处、B 处行为也变了"（render、restrict、去重）。

### P0-3 preset 三副本

`dsh/agent-presets/<preset>/qq-tool-restrict.mjs` 是**被加载的那份**，
`plugins/qq-agent-presets/` 是我以为权威的那份。今天因为改错副本，白名单**一天没生效**且**无任何报错**。

### P1-1 双轨切换有顺序坑

bridge 模式 / 插件模式共用 `state/`，靠 `state/channel-mode.json` 互斥。
**切 A 要先重启 DSH、切 B 要先重启桥接**；反了会空窗或双回复。今天踩过两次。

### P1-2 老会话不重新 apply preset

preset 只在**建会话时**执行 → 改完 preset 代码，老会话永远是旧边界。
今天出现过"代码改了、真机没变、日志也没变"的一小时排查。

### P1-3 依赖 DSH 未文档化 API

`defineTool` / `ctx.agents.create` / `ctx.tools.restrict` / `session/event` 都没有公开契约。
DSH 升级一次，插件可能**静默失效**（今天 11 个 bug 里 4 个是这个原因）。

### P1-4 官方通道上锁待 e2e

代码修完 3 个缺口，7 条 e2e 清单一条没跑（缺测试机器人）。仓库口径已上锁 + 免责声明。

### P2-1 测试偏"脚本级"

130 项审计全是**单元/脚本级**，没有一条真机 e2e 自动化（收消息→回消息的闭环靠人工看日志）。

### P2-2 文档 385 篇，入口多

README / QUICKSTART / UPGRADE / 16 篇 guides / 6 篇 audits / 30+ 篇 release notes。
今天发现 4 处过期示例（版本号、命令），说明**文档和代码没有强绑定**。

### P2-3 单机假设

计划任务、`熔断-*.bat`、`守护启动.bat` 都是 Windows 专属；`state/` 路径按本机布局写死。
虽然 `test-portability.mjs` 保证 `src/` 无硬编码绝对路径，但**部署脚本没有第二套**。

### P3-1 密钥管理靠手工

SnowLuma 的 WS/HTTP token 要手工 `sync-snowluma-token.mjs`；官方 AppSecret 今天重置过一次
（我操作时把明文截进对话，属于流程缺陷，不是代码缺陷）。

## 四、已经做过的缓解（避免重复建议）

- CI 有两套（审计 + 语法/可移植性）
- `plugin/vendor/` 有"副本新鲜度"守卫，`test-packaging`、`check-md-links`、`check-privacy`、`check-lock` 都在审计里
- 工具边界三层（注册期 allow 白名单 / 执行期 guard / 插件侧 restrict）+ 2 秒熔断
- 状态文件有 `version` 字段（`people.json` / `social-v2.json`）
- 官方通道隔离到分仓库 `qq-bridge-official`，做完一次性合并

## 五、希望外部评审回答的问题（按优先级）

1. **分叉漂移**：401/92 这种比例的 fork，长期该怎么活？
   （跟随上游 rebase？还是宣布"独立项目"并停止追？还是只 cherry-pick 安全补丁？各自的成本？）
2. **8,743 行的 bridge.js**：在不停止开发的前提下，最省痛的拆分顺序是什么？
   （哪个模块先抽、怎么保证抽的时候行为不变、要不要先加 characterization test？）
3. **preset 三副本**：有没有比"守卫脚本检查一致性"更根本的解法？
   （单一真源 + 构建产物？还是干脆让 preset 从 npm 包引用？）
4. **双轨切换**：现在的"互斥文件 + 重启顺序"是否已经是最优？
   有没有办法做成"不用重启、自动降级"？
5. **e2e 自动化**：QQ 场景的 e2e 你们怎么做？
   （假 SnowLuma？录播 fixture？还是必须真号？）
6. **测试金字塔**：130 项脚本级测试 + 0 项 e2e，下一步该补哪一层最划算？
7. **文档与代码解耦**：385 篇文档如何避免再次过期？（生成式？还是砍到一个入口？）

## 六、一句话

**功能已经够用，问题都在"长期可维护性"上**：
分叉会越漂越远、单文件会越来越重、preset 副本会再次改错、文档会再次过期。
需要的是**结构性建议**，不是再加功能。
