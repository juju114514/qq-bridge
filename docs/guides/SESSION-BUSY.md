# 「会话繁忙，暂存唤醒原因」是什么，什么时候该管

> **一句话**：日志里这行**本身不是错误** —— 它表示「AI 这一回合还没结束，新的唤醒先排队」。
> 但它有**病态版本**：如果那个回合其实已经丢了（DSH 重启、turn/end 没回来），会话会一直
> 「忙」到 30 分钟租约到期，期间的表现是 **AI 一句不回**。

先跑一条命令判断你在哪一种：

```bash
node scripts/diag-session-busy.mjs
```

它读 `/api/status` 里的 `socialV2Busy`，把判定依据摊开（忙的原因、已忙多久、
`pendingWakeKey` 上锁多久、租约还剩多久、暂存了几条唤醒），并在「看起来卡住」时返回退出码 1。

---

## 一、逐行解释：你在日志里会看到什么

以真实日志为例（私聊会话 `private:2935050388`）：

| 日志 | 含义 | 正常？ |
| --- | --- | --- |
| `[reserved2] 计划唤醒 …，3s 后发送` | 定时器到点，准备投递一次唤醒 | ✅ 正常 |
| `[reserved2] 唤醒 …（private）` | 真正把一个 prompt 投给 DSH | ✅ 正常 |
| `已设置会话模型 … -> deepseek-account/deepseek-flash (high)` | 每回合按当前档位选模型 | ✅ 正常 |
| `[reserved2] 工具统一发送 …：成功 1/1 条` | AI 通过工具把消息发出去了 | ✅ 正常 |
| `[reserved2] 已安排回复检查唤醒 …，45s 后检查` | 发完之后隔一会儿回来看看要不要补一句 | ✅ 正常 |
| `[reserved2] 会话繁忙，暂存唤醒原因 …（private@seq304，原因=pendingWakeKey）` | **这一回合还没结束**，新唤醒先排队（不会丢） | ✅ 正常（**但如果持续 10 分钟以上就不正常**） |
| `[reserved2] 设置远未来有限潜水定时器 …，首段 100 秒后续期` | 定时器单次上限 100 秒，快到点就续期，直到目标时间 | ✅ 正常 |
| `[reserved2] 会话 … 已「繁忙」10 分钟（… 暂存唤醒 N 条）` | **新增的告警**：租约过半还没解除，提示你可能卡住了 | ⚠️ 该看这篇了 |
| `[reserved2] 会话 … 的「繁忙」标记已按 30 分钟租约强制解除` | 租约到期，桥接自己把锁解了 | ⚠️ 自愈了，但要查根因 |

> 所以：**短时间反复出现「会话繁忙」= 群友在连发消息、AI 还在想**，这是设计内的背压。
> 真正要看的是它**持续多久**。

## 二、机制：为什么会「忙」，以及两道保险

桥接判断「忙」有四个来源（任何一个成立就算忙）：

| 来源 | 含义 |
| --- | --- |
| `pendingWakeTimer` | 已经排了一个唤醒定时器，还没到点 |
| `pendingWakeKey` | 已经投递了一个 prompt，还没收到该回合的 `turn/end` |
| `promptQueue.running` / `queue.length` | 该会话的 prompt 队列里有在跑/排队的条目 |
| 回合起始时间在租约内 | 从 DSH 事件流看到回合开始了，且没超过回合租约 |

两道保险（都是为了「宁可自愈，也不要永久哑掉」）：

| 保险 | 时长 | 行为 |
| --- | --- | --- |
| **回合租约** `TURN_BUSY_LEASE_MS` | 30 分钟 | 回合起始时间超出后不再判忙（万一回合其实还活着，回复仍会被收下） |
| **唤醒租约**（本次新增 10 分钟告警） | **10 分钟告警 / 30 分钟强解** | 10 分钟时打 WARN 并给出本篇链接；30 分钟时强制删 `pendingWakeKey` |

> 为什么加 10 分钟告警：30 分钟太久了。用户看到的现象只是「AI 不回」，日志只有一行
> 「会话繁忙」，很容易误判成桥接坏了 —— 让它在**还能自愈的时候**先喊一声。

## 三、正常 vs 卡住

| 判据 | 正常 | 该处理 |
| --- | --- | --- |
| 「会话繁忙」出现后有没有后续动作 | 几秒~几分钟后就看到 `工具统一发送` / `唤醒` | 10 分钟以上**没有任何**发送动作 |
| `diag-session-busy.mjs` 的「回合」列 | < 2 分钟 | > 10 分钟 |
| 「上锁」列 | — （不忙时不显示） | > 10 分钟且不降 |
| 「暂存」列 | 1~2 条 | ≥ 5 条还在涨 |
| 群里/私聊 | 偶尔慢一句 | **完全没反应**，而 `/api/status` 里 `dshReady` 是 true |

## 四、处置（三档，副作用从小到大）

### 1) 等（默认推荐，零副作用）

租约会在 **30 分钟**时自动解除，日志会打：

```
[reserved2] 会话 xxx 的「繁忙」标记已按 30 分钟租约强制解除
```

之后该会话恢复正常唤醒。适合：你不着急、或者不确定是不是真卡住。

### 2) 切一次模式（几分钟，会清空所有 busy 标记）

控制台 → 模式，`reserved2 → chat → reserved2`（或命令行）：

```bash
# 切到 chat 再切回来（会清空 pendingWakeKeys、定时器与队列）
# 具体按钮在控制台「模式」页；切换后日志会打「清理 reserved2 定时器与排队投递」
```

副作用：**正在排队的唤醒/在途 prompt 会被丢弃**（日志里会写明 `drainAllPromptQueues`），
会话需要下一条消息重新触发。适合：多个会话一起卡住。

### 3) 重启桥接（最干脆）

```powershell
# Windows
.\start-bridge.ps1 -Stop ; .\start-bridge.ps1 -Hidden
```

```bash
# Linux
sudo systemctl restart qq-bridge
```

副作用：内存里的 prompt 队列会丢（`state/` 里的会话映射、人格、记忆、表情库都不受影响）。
适合：卡住 + 你要立刻恢复，或者上面两档都不生效。

> ⚠️ **不要**删除 `state/social-v2.json` 来"解决"这个问题——那里存的是记忆/唤醒配置/
> 未读水位，删了等于把这个群的人格与记忆重置。真要重置用控制台的「重置二代状态」。

## 五、卡住的常见根因

| 根因 | 特征 | 怎么确认 |
| --- | --- | --- |
| **DSH 重启把回合丢了** | 日志里 DSH 断连前后各一次「会话繁忙」，之后没有 `turn/end` | `state/bridge.log` 搜 `DSH 不可用` / `事件流` |
| 回合跑到工具卡死 | 有一个工具调用没有返回（比如抓网页超时、语音合成挂住） | `state/tool-calls.jsonl` 尾部是否停在某个工具 |
| 单回合太长（长上下文 + 高 effort） | 回合确实在跑，只是慢；CPU/内存有活动 | `diag` 的「回合」列在动、`token-usage.jsonl` 有增长 |
| 群友连发消息 | 暂存条数在涨，但每隔一会儿会发一条 | 消息洪峰过去后自己恢复 |
| 模型侧 429/超时 | 日志有 `429` / 平台错误 | 见 TROUBLESHOOTING O5 |
| 唤醒限频把投递延后 | 日志 `唤醒频率超限，延后` | 这是**另一码事**，看 E5 |

## 六、预防

1. **别让单回合跑太久**：`dsh.reasoningEffort` 从 `max` 降到 `low/high`（长回合是"忙"的主因）
2. **限制唤醒频率**：`socialV2.wake.maxWakePerMinute` / `maxWakePerHour`
3. **工具要有超时**：抓网页（20s 总预算）、语音合成（子进程）都已有超时，自己加工具时别忘
4. **DSH 重启后观察 1 分钟**：看日志有没有 `重连后恢复了进行中的回合`；有就说明桥接认回了旧回合
5. **别在群里刷屏**：连发会持续制造「暂存唤醒」，虽然不丢，但会让该会话长时间处于忙

## 七、给接手的 AI：看到这行日志的动作清单

```
1. 先跑 node scripts/diag-session-busy.mjs            ← 拿事实，别猜
2. 读「回合 / 上锁 / 租约剩 / 暂存」四列
3. 判定：
     · 全是秒级/分钟级   → 这是正常背压，不要动
     · 有 >10 分钟       → 按第四节处置（等租约 → 切模式 → 重启）
4. 处理完复查：diag 返回 0，且日志出现「唤醒」或「工具统一发送」
5. 要把根因记进 state/bridge.log 的上下文里（DSH 重启？工具卡住？），别只说"重启好了"
```
