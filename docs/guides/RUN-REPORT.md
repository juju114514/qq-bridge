# 运行报告（给"别人出问题时"用的）

> 位置：控制台 → 运维 → **运行报告**；接口：`GET /api/report`（带 `x-console-token`）。
> 只读：不发消息、不改配置、不重启。

---

## 一、它解决什么问题

别人装完说"它不动了"，你第一句话一定是"你那边什么情况"。
让他点一下「生成报告」→「复制」，把文本贴给你——比让他翻日志快一百倍。

更新前后各存一份，就是最直接的前后对比证据（版本 / 重启次数 / 通道状态）。

---

## 二、报告里有什么

| 小节 | 内容 |
| --- | --- |
| 抬头 | 生成时间、版本、buildId、pid、已运行多久、**总体判定**（PASS / WARN / FAIL） |
| 一、检查结论 | 每项一行，`✅ / ⚠️ / ❌` + 一句话说明该怎么做 |
| 二、通道 | DSH / 网关（含累计断开次数与最近恢复时间）/ 官方通道 |
| 三、稳定性 | 24h 重启与退出次数、最近退出码、看门狗事件、内存、磁盘 |
| 四、配置摘要 | 模式、管理员（打码）、白名单数量、官方通道开关与探针 |
| 五、怎么用这份报告 | 贴之前注意什么、更新前后怎么对比 |

---

## 三、判定规则（写死在这里，不是凭感觉）

| 检查 | ✅ ok | ⚠️ warn | ❌ bad |
| --- | --- | --- | --- |
| 连续运行 | ≥ 3 天 | < 3 天 | — |
| 24h 重启 | 0 次 | 1–2 次 | ≥ 3 次 |
| 网关 | connected | — | 非 connected |
| DSH | connected | — | 非 connected |
| 看门狗事件 | 0 条 | ≥ 1 条 | — |
| 内存 RSS | < 800 MB | 800–1600 MB | > 1600 MB |
| 磁盘剩余 | ≥ 5 GB | 2–5 GB | < 2 GB |
| 消息错误 | 0 条 | ≥ 1 条 | — |

> 有任意 ❌ → 总体 FAIL；只有 ⚠️ → WARN；全 ✅ → PASS。

---

## 四、脱敏（可以直接贴出去）

报告在生成时会自动处理：

| 内容 | 处理方式 |
| --- | --- |
| 6 位以上数字（QQ 号、openid） | `159****56` |
| 16 位以上十六进制 | `a1b2…(32位)` |
| 绝对路径 | 替换成 `<repo>` |
| `sk-…` / JWT 形态的令牌 | `<token>` |

> 仍然建议贴之前扫一眼：报告里会显示"白名单有几个群"，但不会显示是哪些群。

---

## 五、怎么取报告

### 控制台（推荐）

运维 → 运行报告 → 生成 → 复制 / 下载 `.md`

### 命令行

```powershell
$tok = Get-Content state\console-token -Raw
# 完整 JSON（含 checks 数组）
curl.exe -s -H "x-console-token: $tok" http://127.0.0.1:3100/api/report

# 只要 Markdown 文本
curl.exe -s -H "x-console-token: $tok" "http://127.0.0.1:3100/api/report?format=md"
```

---

## 六、远程服务器更新前后怎么用

```powershell
# 更新前
node scripts\update.mjs --check > report-before.txt
# （控制台再存一份完整报告）

# 更新后：同样操作 → 对比这三行就够
#   版本 / 24h 重启次数 / 三条通道状态
```

---

## 七、判 FAIL 时的排查顺序

1. **看「二、通道」**：多半是网关没登录（打开 5099 扫码）或 DSH 没起来
2. **看「三、稳定性」的最近退出码**：非 0 就是崩过，去 `state/bridge.log` 找那一段
3. **重启次数 > 3** 且刚更新过：很可能是升级后缺文件/配置不兼容 → 用 `_rollback/` 回滚
4. 还不行：把报告 + `state/bridge.log` 末尾 50 行一起贴出来
