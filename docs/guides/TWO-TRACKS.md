# 两套实现方案：本地注入 vs 官方机器人

> **这一页要记住的核心事实**：qq-bridge 有**两条互不依赖、可各自单独交付**的实现路线。
> 官方渠道**注册门槛高**（个人主体受限、审核、要进群/资质），所以它**不能**当成"桥接的替代品"，
> 而是**第二条轨道**：注册不下来时，本地注入照常能用；注册下来了，两条可以同时跑。

---

## 一、一句话对照

| | **轨道 A：本地注入（个人号 · SnowLuma / OneBot）** | **轨道 B：官方机器人（q.qq.com · QQ Bot）** |
| --- | --- | --- |
| 本质 | 用**你自己的 QQ 号**登录，桥接注入到会话里 | 用**独立机器人号**，走官方 API |
| 注册难度 | **低**：扫码就能用 | **高**：主体认证 / 个人主体仅限自己管理的群 / 平台审核 |
| 能读到 | **群里全部消息**（拟人的地基） | 默认只收 @；群主可开「接收全量消息」 |
| 回复限制 | 基本没有（可分条/撤回/拍一拍） | 被动 5 分钟 / 最多 5 条；主动有频控 |
| 风险 | 非官方协议，可能风控 | 合规，不封个人号 |
| 适合 | 拟人聊天、潜水接话、斗图、点歌、视频理解 | 合规兜底、私聊问答、定时推送 |
| 代码入口 | `src/onebot-ws.js` + `src/bridge.js` | `src/qqbot-official.js` + `src/official-transport.js` |

**两条轨道的代码都在同一个仓库里，但互不 import 对方的运行时**（只有 `official-transport.js` 依赖 `qqbot-official.js`）。
一条挂了不影响另一条；关掉 `official.enabled` 就等于只有本地注入。

## 二、为什么必须分成两套

1. **注册不可控**：官方渠道可能一直批不下来。若把功能都押在官方上，等于把整个项目挂在审核结果上。
2. **身份不通用**：本地注入是"你本人"，官方是"机器人号"；`openid ≠ QQ 号`，白名单、成员、记忆都不能共用一套 ID。
3. **能力不重叠**：官方给不了"读全群消息 + 分条拟人"，本地给不了"合规兜底"。
4. **失败模式不同**：本地掉线（扫码过期/风控）和官方掉线（token 过期/gateway 断）要分别诊断。

## 三、配置怎么切

```jsonc
{
  // 轨道 A：本地注入（默认，路径不变）
  "snowluma": { "wsUrl": "ws://127.0.0.1:3001", "httpUrl": "http://127.0.0.1:3000" },

  // 轨道 B：官方机器人（默认关闭；注册成功后再打开）
  "official": {
    "enabled": false,
    "appid": "1906xxxxxx",
    "secret": "（32 位，放 state/official.json 更安全）",
    "sandbox": false,
    "allowAll": false,
    "allow": []          // 官方会话按 openid 判，不是 QQ 号
  }
}
```

| 想要的效果 | 配置 |
| --- | --- |
| 只有本地注入 | `official.enabled=false`（默认） |
| 只有官方机器人 | `official.enabled=true` + SnowLuma 不登录（桥接会一直重试，不影响官方） |
| 两条同时跑 | 都开；各自独立收消息，各自回消息 |

## 四、共同的部分（不用写两遍）

两条轨道**共用**：人格卡（`roles/`）、长期记忆（`memory-store.js`）、工具白名单与额度、脱敏与出站守卫、DSH 会话管理、控制台。

差异只在最外层：**收消息的协议** 与 **发消息的通道**。所以接新通道时只需要写"适配层"，不要复制业务逻辑。

## 六、给接手的 AI

```
1. 别把官方通道当替代品 —— 它是第二条轨道，注册不下来时 A 照常可用
2. 两条轨道共用业务层（人格/记忆/工具），只在外层写适配
3. openid 不是 QQ 号：官方会话 id 一律 official-<openid>，白名单用 official.allow
4. 官方通道发不了：语音、表情包、分条拟人（≤5 条）、拍一拍
5. 说"官方可用"前必须有证据：scripts/official-probe.mjs 跑出「收到 + 回复成功」
```
