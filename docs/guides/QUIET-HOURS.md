# 静默时段（quietHours）：什么时候该开、怎么开、护栏为什么存在

> 一句话：静默时段 = **消息照收、不唤醒模型**。它不丢消息，只是让机器人在某些小时"闭嘴"。
>
> 相关位置：`config.json` → `socialV2.quietHours`；控制台「会话与审批」页 →「活跃热力图」→「静默时段建议」。

---

## 一、语义（先搞清楚它做了什么）

| 行为 | 静默时段内 |
| --- | --- |
| 收消息 / 记未读 | ✅ 照常 |
| 唤醒模型（@ / 关键词 / 概率 / 拍一拍） | ❌ 被拦下 |
| 管理员指令（`admin`） | ✅ 不受影响（`QUIET_OVERRIDE_REASONS`） |
| 首次引导（`bootstrap`） | ✅ 不受影响 |

配置格式：`[startHour, endHour]`，两个 `0~23` 的整数。

```jsonc
"socialV2": {
  "quietHours": [23, 8]    // 23:00 ~ 次日 08:00（跨零点）
  // "quietHours": null    // 关闭（也是默认状态）
  // "quietHours": [5, 5]  // 起止相同 = 关闭，不允许"静默 24 小时"
}
```

判定逻辑在 `src/quiet-hours.js`：`start < end` 走同日区间，`start > end` 按跨零点处理。

---

## 二、什么时候该开

**该开**：

- 你的群有明显的"深夜热闹、凌晨安静"节奏（看热力图确认，不要凭感觉）
- 机器人曾经在半夜回话，吵到人
- 你想省 token：深夜那几小时的唤醒本来大多也是无效参与

**不该开**：

- 群是**全天候工作群**（客服、值班），任何时刻都有人 @ 它
- 群里有人依赖它做深夜功能（点歌、查资料、定时提醒）
- 你只有一两个群、消息量本来就低——静默收益抵不过"漏回"的风险

**判断依据不是感觉，是热力图**：控制台「会话与审批」页，7×24 网格里哪几格最暗，就是候选窗口。

---

## 三、热力图的口径（这里踩过坑）

热力图与建议**只统计入站消息**：排除机器人自己发的（`isSelf`）与斜杠命令。

为什么强调这件事——实测数据：

```
样本 275 条 → 机器人自己发的 110 条（40%）
「23–8」窗口内：全部消息 114 条  vs  仅入站 43 条
```

如果把自己说的话也算成"群活跃"，会把"我说得多"误判成"群里热闹"，
让"值不值得改"的数字夸大 2.6 倍。界面上会写明样本量与时间跨度，
避免把两天的样本当成长期作息。

> 进阶口径（尚未做）：只统计"本来会触发唤醒"的消息。这需要回放 `evaluateWakeTrigger`，
> 而概率触发带随机性、回放不稳定；`decision-trace` 缓冲只有 80 条，样本太小。
> 目前用"入站 + 去命令"这个口径，并把它写在界面上。

## 四、护栏开关：为什么默认要求「覆盖深夜」

算法本身是：把 7×24 压成 24 列，滑窗找**连续 8 小时消息最少**的窗口。

**但"消息最少"不等于"该静默"**。实测给出过这样的建议：

```
不限深夜的最优解：05:00–13:00（窗口内 1 条）
真实每小时分布：  03:0 04:1 05:0 … 09:0 10:1 11:0 12:0 13:17 14:18
```

05–13 之所以"安静"，是因为**上午没人说话**，不是因为"该静默"。
按这个窗口配下去，上午 10 点有人 @ 它也不醒 —— 那是上班时间关机，不是静默。

所以界面上有一个**默认勾选、可以取消**的开关：

```
☑ 只推荐覆盖深夜（02:00–06:00）的窗口
  开：候选窗口必须完整包含 02–06 点，避免算法挑出「白天全静默」（上午有人 @ 也不醒）。
  关：不限深夜，只看消息最少 —— 可能选出白天窗口，机器人会在上班时间保持沉默。
```

- 默认**开**（护栏生效）
- 取消后立即重算，并给出"不限深夜"的候选与数量
- 若最终选中的窗口仍不覆盖深夜，界面会显示明确警告
- 偏好记在 `localStorage.quietRequireDeepNight`，下次打开保持

护栏的判定是 `coversDeepNight(start, len)`：窗口必须完整包含 `02, 03, 04, 05` 这四小时。

## 五、一键采用（四道保护）

界面上「采用建议（HH:00–HH:00）」按钮点击后：

1. **重新拉数据重算** —— 绝不把页面打开时的旧建议写进去；建议变了就提示"已更新，请再看一眼"
2. **二次确认** —— 显示 `[旧值] → [新值]`、影响面、样本量
3. **原子写 + 热更新** —— 复用 `POST /api/socialV2/config`，内部是 `atomicWriteJson`（先写临时文件再 rename，中断不会写坏配置）
4. **回读校验 + 失败回滚** —— 写完 GET 复核；不一致或失败就把旧值写回去并弹出错误

它改的就是一个字段：

```jsonc
"socialV2": { "quietHours": [2, 10] }
```

## 六、手动配置

不想用控制台，直接改 `config.json` 也行（改完不需要重启？**需要**——见下）。

```powershell
# 1. 备份
Copy-Item .\config.json .\config.json.bak

# 2. 编辑 socialV2.quietHours（示例：02:00–10:00）
# 3. 重启桥接
schtasks /end /tn qq-bridge; schtasks /run /tn qq-bridge
```

控制台里的「采用建议」走的是热更新（`setCfg`），**手工改文件要重启**才生效。

## 七、排查

| 现象 | 先看这里 |
| --- | --- |
| 该静默的时候它还是回话 | 是不是管理员指令 / bootstrap？（这两类不受静默限制）；`[start, end]` 是不是写成了 `[x, x]`（= 关闭） |
| 静默时段内它一声不吭，白天也不吭声 | 窗口是不是选到了白天？看热力图 + 护栏开关 |
| 想知道某条消息为什么没唤醒 | 控制台「诊断与健康」→ 唤醒漏斗（看"已暂停 / 未命中"哪一类） |
| 改完没生效 | 手工改文件要重启；控制台按钮是热更新 |
| 日志里怎么确认 | 启动时的静默区间会打印；唤醒被拦时 trace 里有 `唤醒 / 已暂停` |

---

## 八、建议的使用节奏

1. 先**别开**，让它跑一周，让热力图有足够样本
2. 看「会话活跃时段 Top 8」和「静默时段建议」，确认最暗的那段确实是深夜
3. 勾着护栏（默认）点采用，观察两三天
4. 如果发现"深夜其实有人需要它"（比如夜班群），把窗口收窄，或直接关掉

**静默不是越久越好**：它的收益是"少打扰 + 省 token"，代价是"可能会漏回"。
用数据选窗口，用观察调窗口。
