## 补传 diff 后的结论

diff 与 ZIP 中的 `src/instance-lock.js` 一致，没有改变我上一轮的判断。反而，完整 diff 让两个 guard 问题可以明确定位到具体代码。

### 需要优先处理的两个问题

P2-1：多个进程并发回收 stale guard，可能删除新 guard。

`withGuard()` 中：

```
if (!isPidAlive(holderPid)) {
  fs.rmSync(guardFile, { force: true });
  continue;
}
```

这里没有验证 `rmSync()` 删除的仍然是刚才检查过的那个 guard。两个回收者可能都检查旧 guard 为 stale，先后执行删除；后执行者可能删除另一个进程刚创建的新 guard。

这属于真实的 check-then-delete 竞态。现有 generation token 只保护实例锁，不保护 `.guard` 文件。

P2-2：损坏或尚未写入 PID 的 guard 被当作死持有者回收。

`openSync('wx')` 创建 guard 后，代码才写入 PID：

```
const fd = fs.openSync(guardFile, 'wx');
try { fs.writeSync(fd, String(process.pid)); } catch { /* ignore */ }
```

创建与 PID 写入之间存在窗口。如果创建者暂停，其他进程在超过 5 秒后读到空文件，会将 `holderPid` 设为 `0`，随后 `isPidAlive(0)` 返回 false，删除 guard。

所以我维持上一轮意见：不能把 PID 无法读取等同于 PID 已死亡。 未知状态应该保守拒绝回收。

### 测试名称也应修正

diff 中测试注释声称包含“真实双进程屏障”，但代码实际是：

- 子进程 A 取得实例锁；
- A 等待父进程创建信号文件；
- 父进程 B 尝试认领；
- 因 A 的锁仍新鲜且 PID 存活，B 被拒绝。

它没有让 A 在 `withGuard()` 内暂停，也没有真实验证 guard 的回收竞态。

建议将测试名改为：

`A 子进程持有实例锁时 B 认领被拒`

核心 TOCTOU 测试继续标注为同进程确定性模拟。真实双进程屏障测试仍然是未覆盖项。
