## 1. 两个网关不是等价品（最容易被忽略）

| 能力 | SnowLuma（主） | NapCat（备） |
| --- | --- | --- |
| 收发消息 / 事件 | ✅ | ✅ |
| 好友列表 | ✅ | ✅ |
| 读收藏表情 | ✅ | ✅ |
| **写收藏表情 / 改备注** | ✅ | ❌ 真没有 |
| 端口 | 3000 HTTP / 3001 WS | 3000 HTTP / 3001 WS |

**关键：区分两种失败。**

| 返回 | 含义 | 处理 |
| --- | --- | --- |
| `不支持的Api xxx` | 网关真没这个能力 | 换网关，改代码没用 |
| `file: is required` | 能力有，只是参数不对 | 查该网关需要的参数名 |

`scripts/probe-gateway-caps.mjs` 就是为这件事写的：

```powershell
node scripts/probe-gateway-caps.mjs              # 只读探测，不污染收藏夹
node scripts/probe-gateway-caps.mjs --write      # 真写一张（会进收藏夹）
```

它按四态判定：`[可用]` / `[支持]（缺参数）` / `[不支持]` / `[失败]`。

## 2. 通道自检（3 条命令定位到底断在哪）

```powershell
# ① 网关端口在不在
Get-NetTCPConnection -LocalPort 3000,3001 -State Listen

# ② 账号登没登（这一步同时验证 端口通 + 令牌对 + 已登录）
Invoke-RestMethod http://127.0.0.1:3000/get_login_info -Method Post `
  -Headers @{Authorization="Bearer <token>"} -ContentType 'application/json' `
  -Body '{"action":"get_login_info","params":{}}'

# ③ 桥接连没连
Get-Content state\bridge.log -Tail 20 | Select-String '已连接|1006'
```

判断：

| ① | ② | ③ | 结论 |
| --- | --- | --- | --- |
| 没监听 | 失败 | 1006 | 网关没启动，或账号没登录 |
| 监听 | ok | 1006 | **令牌不匹配**（见 §4） |
| 监听 | ok | 已连接但发不出 | 发送走 HTTP，检查 `httpToken` |

## 3. 表情收藏为什么不生效（三层坑，逐层排查）

### 3.1 网关不支持

NapCat 的 `add_custom_face` 返回 `不支持的Api`。→ 只能在 SnowLuma 上做。

### 3.2 桥接取不到图

日志 `AI 收藏表情失败 group:xxx: `（冒号后面空）→ 说明是 WS 断连导致错误对象为空，
不是收藏逻辑的问题。先修 §4。

### 3.3 模型不去调工具（最麻烦）

实测三种文案，模型行为不稳定：

| 文案 | 结果 |
| --- | --- |
| "没意思就忽略" | 直接忽略 |
| "本轮先调 qq_get_sticker_image 再决定" | 图本来就在上下文里，它觉得多余 → **整段跳过** |
| "图已在上下文，不必再调看图工具，直接判断收不收" | 偶尔调，偶尔不调 |

**结论：不要指望提示词让模型稳定收藏。** 要确定性就做成桥接侧自动收藏（带配额与过滤）。

### 3.4 数据在哪些文件

| 文件 | 内容 |
| --- | --- |
| `state/sticker-notes.json` | 笔记：含义 / 分数 / 状态 / scope（group 与 private 分开） |
| `state/sticker-curate-token` | 独立策展服务（3181）的令牌 |
| 网关 `fetch_custom_face_detail` | 真实收藏夹（**注意 count 参数！**） |

> ⚠️ 踩过的坑：用 `count=50` 读收藏夹得到 50 条，误以为"基线 50"，
> 后来用 `count=100` 得到 66 条，差点误判"收藏成功了 16 张"。
> **对比前后必须用同一个 count，且要大于总数。**

## 4. 双 token：`accessToken` 与 `httpToken` 必须分开

SnowLuma 的 HTTP 服务和 WS 服务**各有一个 accessToken**：

```json
"networks": {
  "httpServers": [{ "port": 3000, "accessToken": "A..." }],
  "wsServers":   [{ "port": 3001, "accessToken": "B..." }]
}
```

| 用途 | 用哪个 token |
| --- | --- |
| 桥接的 HTTP 调用（发消息、拉列表、收藏） | **httpToken** |
| 桥接的 WS 连接（收事件） | accessToken |

**症状对照**：

| 现象 | 原因 |
| --- | --- |
| HTTP 返回 `401 unauthorized` | 用了 WS 的 token 去打 HTTP |
| 日志刷 `1006`，但 `get_login_info` 正常 | 用了 HTTP 的 token 去连 WS |

桥接配置：

```json
"snowluma": {
  "httpUrl": "http://127.0.0.1:3000",
  "wsUrl": "ws://127.0.0.1:3001",
  "accessToken": "<ws token>",
  "httpToken": "<http token>"
}
```

**不要试图"把两个 token 改成一样"**：SnowLuma 不会热加载，
改完必须重载账号，而重载会把当前 QQ 会话踢掉（日志 `session closed`）。

## 5. 改了 config 却没生效 → loadConfig 是显式装配字段的

`loadConfig()` 只挑它认识的字段。新加的配置段（`official` / `inject` / `curator` /
`privateAccess` / `gateway`）如果忘了登记，读出来就是 `undefined`，**而且不报错**。

表现为"配置写了、日志没反应"。

**兜底写法**（模板）：

```js
function someEnabled(cfgIn) {
  const v = cfgIn?.socialV2?.xxx?.enabled;
  if (v === true) return true;
  if (v === false) return false;
  // 内存里没有 → 回读配置文件再判一次
  for (const p of [path.join(ROOT, 'config.json'), path.join(process.cwd(), 'config.json')]) {
    try {
      const raw = JSON.parse(fs.readFileSync(p, 'utf8').replace(/^\uFEFF/, ''));
      if (raw?.socialV2?.xxx?.enabled === true) return true;
    } catch { /* 下一个 */ }
  }
  return false;
}
```

## 6. 改 `bridge.js` 的固定动作（不按这个顺序就会翻车）

`bridge.js` 约 1.2 万行，行号会随每次提交漂移。

```
1. grep 出真实锚点（别信上一次的行号）
2. 读锚点前后 20 行，确认变量在该作用域可见
3. 备份：Copy-Item bridge.js D:\QQBot\temp\bridge.js.bak-<用途>
4. 改 → node --check → node scripts/test-audit.mjs
5. 复制到 live 目录 → 重启 → 看日志/端点
6. 提交（一次一片）
```

### 6.1 新模块必须登记到 VM 夹具

审计用的是 VM 沙箱，模块要按名字注入。忘了就会：

```
ReferenceError: createPendingQueue is not defined
Audit suite: 59/67 scripts passed     ← 一次改动让 8 个测试红
```

修法：`scripts/audit-bridge-harness.mjs` 里加

```js
import * as newModule from '../src/new-module.js';
// 并在展开处加 ...newModule
```

**踩过两次**（`officialTransport`、`sticker-pending`）。

### 6.2 helper 不要引用 `main()` 的局部变量

在模块顶层写 helper 却用 `cfg`（它是 `main()` 里的局部变量）会抛
`ReferenceError: cfg is not defined`，而外层 `catch { return '' }` 会**把错误吞掉**，
表现为"功能静默不生效"。

修法：把 `cfg` 作为参数传进去（`fn(key, cfg)`）。

### 6.3 调试日志要落文件，不要用 console.log

桥接是隐藏窗口启动，`console.log` 全部丢失。用：

```js
function stickerDebug(msg) {
  if (process.env.QQB_STICKER_DEBUG !== '1') return;
  try { fs.appendFileSync(path.join(STATE_DIR, 'sticker-debug.log'), new Date().toISOString() + ' ' + msg + '\n'); } catch {}
}
```

## 8. 群聊与私聊必须隔离（表情偏好会串味）

同一条表情记录带 `scope`（`group` / `private`），三层保证：

1. 存储层：`normalizeScope()` 非法值兜底成 `private`
2. 取用层：`buildStickerNotesHint(notes, scope)` **不传 scope 返回空串**
3. 提示层：限幅 3 条 / 60 字 / 固定前缀「（选图参考，不改语气）」

硬规则：**没有 scope 就不生效**，宁可少给提示，也不能让群聊内容串进私聊。

## 9. 私聊：只接好友，临时会话一律拒

SnowLuma/NapCat 的私聊事件：

```
message_type = 'private'
sub_type     = 'friend' | 'group' | 'other'
```

- `'friend'` → 好友私聊，可接
- `'group'` → **临时会话**（从群发起），网关实现不稳（消息能进、回复发不出）→ 拒
- 判定不需要 `get_friend_list`：`sub_type` 本身就说明了关系

配置：`socialV2.privateAccess`（**新装默认 `enabled=false`**）。

## 15. 可移植性：测试不许写死本机路径（含"守卫为何失效"）

### 15.1 事故

2026-10-29 外部审计在 Linux 上跑，5 个测试红。原因不是代码坏，而是测试里写死了作者本机路径：

```js
// ❌ 换目录 / 换系统必红
const m = await import(pathToFileURL('D:/QQBot-open/qq-bridge/src/x.js').href);
```

受影响文件：`test-gateway-select` / `test-private-access` / `test-sticker-hint`（2 处）/
`test-sticker-notes` / `test-sticker-pending` —— 共 6 行。

### 15.2 正确写法

```js
// ✅ 跟随测试文件自身位置
const m = await import(new URL('../src/x.js', import.meta.url).href);
```

验证办法（不依赖 CI）：把仓库整体复制到别的目录再跑那几个测试。

### 15.3 守卫为什么没拦住（更值得记住）

`scripts/test-portability.mjs` 本来就是为了拦这个，但它有：

```js
const SKIP = (rel) => /(^|\/)test-[^/]*\.mjs$/.test(rel)   // test-*.mjs 整类跳过
```

理由写的是"里面的盘符是样例路径"——**这个豁免本身合理**（测试确实要写
`C:\Users\someone\config.json` 这类样例来验证"外部绝对路径被拒"），
但它把"真的加载路径"也一起豁免了，于是**守卫对自己要防的那类问题完全失效**。

### 15.4 最后采用的修法：两条规则并存

| 规则 | 作用 | 为什么这样 |
| --- | --- | --- |
| 保留 `SKIP`（测试文件跳过盘符扫描） | 避免 19 处合法样例变成噪声 | 样例路径本来就该出现 |
| **新增专项检查**：`test-*.mjs` 里出现 `pathToFileURL('X:/...')` 或 `import('X:/...')` 即失败 | 精确命中"用绝对路径加载模块" | 这一类**只有 bug，没有样例** |
| 检查自身跳过 `test-portability.mjs` + 纯注释行 | 防止"守卫自己的反例把自己咬红" | 踩过一次 |

**做守卫的经验**：先问"我要防的那一类，能不能和其它正常情况区分开"。
分不开就整类豁免 + 另加专项检查，不要用"行级豁免注释"硬撑——那个方案试过，
19 处样例全要加注释，噪声大到没人会维护。

### 15.5 CI 兜底

`.github/workflows/audit.yml` 在 Ubuntu + Node 20 上跑：

```yaml
- run: node scripts/test-audit.mjs
- run: node scripts/test-portability.mjs
```

作用：**"clone 即全绿"不再只靠自觉**。本机绿 + CI 绿，才算真的绿。

### 15.6 给以后加测试的人三条

1. 加载源码一律 `new URL('../src/x.js', import.meta.url)`，不要用盘符
2. 需要"样例绝对路径"时，那是**字符串常量**，不是加载参数 —— 两者别混
3. 改完顺手想一句："换台机器 / 换个目录还绿吗？"

## 16. 一条命令启动（自动识别网关）+ 一个必踩的 token 坑

### 16.1 `scripts/start-all.ps1`

双击桌面「启动QQ机器人」就是跑它。它做的事：

```
1) 用 config.json 里的 SnowLuma token 探 3000
2) 不通 → 用 NapCat 的 onebot11_*.json token 再探
3) 都不通 → 启动 SnowLuma，等 40 秒
4) 还不通 → 启动 NapCat（会先退出 QQ 客户端：两者不能同时登录）
5) 按实际可用的网关**改写 live config 的 token**
6) 启动桥接，打印状态表
```

| 用法 | 说明 |
| --- | --- |
| `.\scripts\start-all.ps1` | 自动识别 |
| `.\scripts\start-all.ps1 -StatusOnly` | 只看状态，不启动任何东西 |
| `.\scripts\start-all.ps1 -Preferred napcat -Qq <号>` | 强制走备选 |

### 16.2 坑：SnowLuma 多账号配置里有一份是**空的**

```
D:\QQBot\snowluma\config\
  onebot_<机器人号>.json   ← httpServers / wsServers 都有 token（正确）
  onebot_<你的大号>.json   ← httpServers 是空的！
```

第一版 `start-all.ps1` 按"第一个含 networks 的文件"取值，正好取到大号那份 →
**把空 token 写进 config.json** → 桥接 401 + WS 1006 无限重连。

日志里的关键一行（很容易被忽略）：

```
⚠️ token 自愈失败：所有候选 token 都被拒绝（401）
   当前账号的 token 可能还没写进 SnowLuma 的 config
```

**正确取法**：只认同时满足下面三条的那份配置

```
httpServers 非空 AND wsServers 非空 AND 两者 accessToken 都非空
```

### 16.3 顺带记住：DSH 端口会漂

DSH 每次重启，Web GUI 端口可能变（例如 58529 → 58467）。桥接会自己发现并改写
`config.json`：

```
[dsh] 端口漂移：http://127.0.0.1:58529 → http://127.0.0.1:58467（原因：fetch failed）
[dsh] 已用新端口连通
```

所以看到这条不用担心，也**不要在 config 里写死 DSH 端口**。

### 16.4 启动失败的三种典型现场

| 现场 | 原因 | 处理 |
| --- | --- | --- |
| 5099 在听、3000 没有 | SnowLuma 起来了但账号没登录 | 打开 5099 → 进程注入 → 加载 QQ |
| 3000/3001 在听、桥接 1006 | token 不匹配（HTTP/WS 各一个，或多账号取错文件） | 见 16.2 |
| 桥接起来了但控制台 3100 没有 | 桥接进程被守护脚本判为"已有实例"跳过了 | 直接 `node src/bridge.js` 或重启守护 |

## 17. SnowLuma Hook 退化：能发不能收

> 来源：一位从 AstrBot 迁过来的真实用户报的现象（2026-10）。

### 症状

| 现象 | 说明 |
| --- | --- |
| 机器人**能发消息**，但群里说话它毫无反应 | 出站正常、入站为 0 |
| 日志没有 `收到`，也没有报错 | WS 连着、心跳正常，就是没有事件 |
| 重启 SnowLuma 后短暂恢复，过一阵又不行 | 典型的 Hook 退化 |

### 根因

SnowLuma 依赖注入 QQ 进程内的 Hook 来拿事件。QQ 客户端长期运行后，
注入的 Hook 可能失效（进程还在、连接还在，但事件不再回调）。
**这不是桥接的问题**，桥接只是收不到事件。

### 判定三步

```powershell
# ① 桥接这侧有没有收到（最直接）
Get-Content state\bridge.log -Tail 40 | Select-String '收到|official'

# ② 网关这侧有没有"看到"消息（SnowLuma 日志里有 Event 行）
Get-Content D:\QQBot\snowluma\logs\snowluma-$(Get-Date -f yyyy-MM-dd).log -Tail 20 |
  Select-String '\[Event\]'

# ③ 直接问网关要一条状态
curl http://127.0.0.1:3000/get_login_info -H "Authorization: Bearer <http token>"
```

| ① | ② | 结论 |
| --- | --- | --- |
| 无 | 有 | 桥接侧订阅/路由问题 |
| 无 | 无 | **Hook 退化**（重载账号） |
| 有 | 有 | 正常，去查唤醒条件 |

### 处理

1. SnowLuma 控制台 →「进程注入」→ **重新加载 QQ**（不用重扫码通常也能恢复）
2. 或者彻底重启 QQ + SnowLuma
3. 若频繁退化：把网关切到 NapCat（`gateway-select` 会自动降级，也可手动
   `scripts\start-all.ps1 -Preferred napcat`）——NapCat 走原生注入，长期稳定性更好

### 与"双 token"的区别（两个都像"收不到"，但成因不同）

| | Hook 退化 | 双 token 搞错 |
| --- | --- | --- |
| 出站（发消息） | ✅ 正常 | ❌ 401 |
| 网关日志有 Event | ❌ | ✅ 有 |
| 修法 | 重载账号 | 见 §4，HTTP/WS token 分开填 |

## 18. 网关内置命令 `#sl`（群友也能用）

### 它是什么

> 命令速查见 [COMMANDS.md](../COMMANDS.md#网关内置命令不是本仓库实现群友也能用)。

`#sl` **不是桥接的命令**，是 SnowLuma 自己的状态卡命令。在群里发 `#sl`，会回一张：

```
SnowLuma 状态
版本: 2.1.1
平台: win32-x64
运行时长: 4小时 45分钟
```

配置在 `D:\QQBot\snowluma\config\onebot_<QQ>.json`：

```json
"statusCommand": {
  "enabled": true,
  "swallow": false,        // false = 回完状态后，这条消息仍转发给桥接
  "cooldownSeconds": 5,
  "trigger": "#sl"
}
```

匹配是**整条消息完全相等**（忽略大小写与首尾空格）：`#sl` + 图片这种混合消息不触发。

### 安全性评估（结论：可以开放，但要知道它暴露了什么）

| 暴露的信息 | 敏感度 | 说明 |
| --- | --- | --- |
| SnowLuma 版本号（2.1.1） | 低 | 知道版本理论上可对照已知漏洞，但这是本地注入工具，不在公网暴露 |
| 平台（win32-x64） | 低 | 只说明是 Windows 64 位 |
| 运行时长 | 极低 | 甚至能反应"你有没有重启过" |
| **令牌 / QQ 号 / 配置** | **不涉及** | 命令实现只读这三个字段，不回任何凭证 |
| 能否被用来改配置 | **不能** | 纯查询，无副作用 |

**唯一需要注意的两点**：

1. **`swallow: false` 时这条消息会继续进桥接** → 模型可能再回一句，出现"状态卡 + AI 附和"的双回复。
2. **5 秒冷却只限制频率，不限制身份** —— 群里任何人都能发。

### 三种处理方式

| 目标 | 配置 | 效果 |
| --- | --- | --- |
| 谁都别用 | `"enabled": false` | 完全关闭 |
| **群友可用，但别让 AI 掺和**（推荐） | `"swallow": true` | 状态卡照出，消息不进模型 |
| 只让知道暗号的人用 | `"trigger": "#sl-admin"` | 触发词换成不显眼的 |

改完需要让 SnowLuma 重新加载账号（可能踢一次登录）。

### 和桥接命令的区别（重要）

仓库里有**两套命令**，权限模型完全不同：

| 来源 | 例子 | 权限控制 |
| --- | --- | --- |
| **桥接命令**（`bridge.js` 里硬编码） | `/status` `/role` `/reset` `/silent` `/active` | ✅ 有，`isOwner` 硬闸，非管理员直接回"管理命令仅管理员可用" |
| **网关命令**（SnowLuma 内置） | **`#sl`** | ❌ 没有，只能靠开关 / 触发词 / 冷却 |

所以：**需要权限的命令写进桥接**，纯展示型的（如 `#sl`）交给网关没问题。

### 想让 AI 知道这个命令吗

`#sl` 由网关直接处理，模型看不到（除非 `swallow: false`）。
如果你希望模型在有人问"你跑了多久"时主动提示"可以发 `#sl` 看"，那就把这条写进人格卡 / 初始提示词 —— 它只是话术，不需要代码支持。
